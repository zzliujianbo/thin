# Offline test workflow

Use `python3 -B tests/run.py <group>` from the repository root. The runner defaults to Debug and `-j1`, gives test children a 32 MiB stack, drops DAC-bypass capabilities when run as root, and records logs, timing and source identities under `.zig-cache/workflow/`. Use `--optimize ReleaseSmall`, `-j`, and the `--ssh-include`/`--ssh-library` options as needed. `preflight` checks source syntax and formatting without executing product tests.

- `unit` and `unit-full` both run the same complete, unfiltered unit artifact.
- Linux-only `unit-sharded` reuses the existing six compiled owner artifacts (fast/ui/app/core/integration/daemon), with entry-local standard Run steps. Before any shard executes, a metadata-only guard queries the full compiled unit artifact and all six shard artifacts, requiring disjoint shard sets whose union equals full after excluding the exact root bookkeeping cases. The guard never runs full unit cases or needs fixture servers; unknown, missing, extra or duplicate cases fail. A cold sharded invocation therefore also compiles the full unit artifact for inventory; warm invocations can reuse all compiled artifacts but still query metadata and actually execute the shards. Individual owner entries, including fast, do not depend on this guard or full compilation. For controlled unit-only process parallelism use `python3 -B tests/run.py unit-sharded -j2`; this is not a claim that sharding is always faster. The unfiltered unit and release full gates are unchanged. On macOS use the existing `fast`/`unit-full` entries; the sharded and owner-daemon entries explicitly fail only when selected. Other owner groups have no cross-platform acceptance claim.
- `fast` selects the explicitly designated pure-computation files. `unit-ui`, `unit-app`, `unit-core`, `unit-integration`, and `unit-daemon` select individual layout owner groups. Each uses a generated root importing only selected owners, splitting the compilation dependency graph rather than merely filtering tests. Fast does not link SSH or native shims. These are not full coverage gates.
- `focus --filter 'distinctive named test'` filters the complete unit tree; an empty filter or a filter matching no product test fails. `render` runs the existing rendering selection.
- `app` runs the existing application acceptance fixture, not the unit-app group. `interaction`, `communication`, and `streaming` remain targeted fixture suites. `full` preserves the complete offline gate including the standalone Memory, HTTP and PTY fixtures.

The build composes external test fragments into stable local-cache `generated-tests/<canonical-project-path-hash>/<variant>/src` trees according to `tests/layout.json`. The all, driver and individual group variants are isolated. The namespace hashes only the canonical project path, not source content, so separate checkouts sharing a local cache do not overwrite each other's trees and unrelated edits do not relocate generated inputs. Existing cache trees need no migration. Composition runs before each dependent compilation and only changes output files whose bytes differ, allowing ordinary compiled-artifact reuse. Test runs themselves are not cached: a warm invocation still executes test cases. The product executable, `check`, and exported presentation module use production `src` directly and do not depend on Python or composition.

Keep PTY/communication and full timing gates at the default `-j1`, running them separately rather than concurrently with shards or other timing gates. `-j1` alone does not guarantee mutual exclusion of Run steps. On Linux, the `full` entry runs its own daemon latency fixture only after every other original full prerequisite completes (including tooling, unit, Memory, HTTP, SSH, probes, viewport and queued fixtures). A failed prerequisite prevents that final daemon fixture from running. The `communication` entry similarly runs its own daemon fixture after subscription and SSH complete, without depending on the rest of full. Each entry runs daemon once; direct `test-daemon` remains independent, and non-Linux full retains its existing direct dependencies without a daemon gate. These are entry-local dependency fences, not a global lock or a guarantee for explicitly combined targets. No threshold, sample count or request budget is changed. Historical latency failures, including #37, remain recorded; this ordering neither proves prior overlap nor establishes or resolves their root cause.

Runner logs may contain test output and should be handled as private diagnostic artifacts. Any cached `run test` node invalidates fresh-run evidence, even alongside positive totals; cached compilation and Node fixture labels are not cached test nodes. Focused and unit selections require positive test-count evidence and reject zero-case run nodes. Sharded runs additionally require fresh positive `run test [group]` evidence for each of fast/ui/app/core/integration/daemon, not just a global sum. Missing or duplicate identities, cached nodes and zero-case nodes fail; different identities may have identical counts. Source hashes cover `build.zig` and recursive `src` and `tests` inputs, not the compiler or system dependencies. They are checked before and after each run. No test here calls a real model API; network fixtures use owned local services.
